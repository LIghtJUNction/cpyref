## 被测软件与执行环境

2026-10-14 19:39 UTC 开始的正式批次先解析最新 main，再安装 `8d649a45e565387ee58150a13fc082864183aad1`，二进制版本显示 `cpyref 0.1.1`。使用 `cargo install --git ... --rev ... --locked`，不是 crates.io 已发布包，也不是旧 PATH 二进制。完整 [安装命令](results/38625471864/install-command.txt) 和 [安装日志](results/38625471864/install.log) 已保存。

正式执行仅在一台 Linux x86_64 GitHub Actions 机器上完成。35 个独立任务，每组每题预热一次、正式重复 20 次，顺序随机，缓存未清空。6 项使用真实仓库文件，29 项使用明确构造的工作流程材料。数据不是从实际用户 Agent 会话抽样得到的。

[执行记录](https://github.com/LIghtJUNction/cpyref/actions/runs/38625471864) 已完成；[Rust 验证](results/38625471864/rust-validation.json) 的格式、测试、Clippy 三项退出码均为 0。

## 正确率：本轮没有测出相对于正确 Python 脚本的优势

| 组 | 正常目标完成 | 正确拒绝 | 不支持 |
|---|---:|---:|---:|
| cpyref | 500/500 | 200/200 | 0 |
| Python 字节处理 | 500/500 | 200/200 | 0 |
| 无损正文往返 | 500/500 | 140/140 | 60 |
| 原生 cp（仅适用任务） | 160/160 | 不参测 | 0 |

前两组在共同的 35 项任务上都满足全部验收。700 次运行不是 700 个独立任务；拒绝歧义、损坏、错误空间、未授权覆盖等 200 次操作也不是复制了 200 份内容。

Python 对照由基准作者预先写好严格选择、文件保护、阶段快照和上下文分配。结果说明正确写出的无 cpyref 脚本同样能完成这些任务，不能说明真实 Agent 每次都能写对。cpyref 同样使用预先写好的调用方案，不包含模型发现工具、理解参数、纠错和规划的难度。

正文往返组的三类不支持项独立保留：项目隔离、组隔离和保存数据损坏验证。不把这些项目当成通过，不把其缺少的能力变成对 cpyref 有利的整体成功率比较。

## 耗时：存在明确的适用边界

下表为每题 20 次正式运行的中位数，单位毫秒。完整逐题 p95 保存在 summary.json。

| 任务 | cpyref 流程 | Python 流程 | 原生 cp |
|---|---:|---:|---:|
| 从文件提取长链接再写入 | 4.400 | 29.218 | 不适用 |
| 按行复制 CRLF 文本 | 3.991 | 28.978 | 不适用 |
| README 写入十个目标 | 19.590 | 33.461 | 23.139 |
| 复制 256 KiB 二进制文件 | 5.761 | 29.493 | 2.551 |
| 复制 1 MiB 文件 | 11.059 | 30.345 | 2.816 |
| 在唯一标记前插入 | 33.087 | 29.111 | 不适用 |
| 替换标记间区域 | 33.339 | 29.213 | 不适用 |
| 追加内容 | 32.727 | 28.959 | 不适用 |

本次许多 cpyref 流程比新启动的 Python 进程快。但这是进程级比较，包含 Python 运行时和所用标准库启动开销，不是 Agent 总任务时间提升，也不是 Rust 对 Python 的普遍性能结论。

简单的单目标整文件复制中，系统 cp 通常更快。cp 对照不执行 cpyref 的持久快照、完整摘要检查和显式同步写盘，不能把不同承诺隐藏在同一速度排名中。十目标例外与本次配方有关：cp 启动十次，Python 启动一次，cpyref 启动一次 copy 加十次 paste。

插入、局部替换、追加的 cpyref 组包含 `copy → paste 到片段文件 → 通用 Python 编辑目标`，比直接 Python 流程约慢 13%—15%。**这四类组合任务（还包括重复目标标记的拒绝）不算原生 paste 能力测试。**

据此可提出一个待验证的开发方向：原生插入、局部替换和追加接口可能减少临时文件与辅助进程。将来实现后应增加独立原生组，保留现有组合组与 Python 组，不改旧结果，不先宣称优化幅度。

## 参数流量：不能换算成模型 Token 或费用

长链接任务的本测试进程边界字节数中位数为：cpyref 152，Python 859，无损正文往返 12,195。这里统计规范化的命令参数 JSON、stdin、stdout、stderr。

这不是模型输入/输出 Token。无损往返程序没有调用模型；它也没有真的逐个字符生成内容。Python 直接操作文件时本来就不需要把正文传给模型。因此不能从这张表得出“没有 cpyref 必须重写原文”，更不能把字节减少率当作模型费用减少率。

另外，进程数不等于 Agent 工具调用轮数。真实 Agent 可以在一次终端调用中串联多个命令；本基准没有测量这种模型交互选择。

## 证据核对与尚未完成的部分

单独的 [核对工作流](https://github.com/LIghtJUNction/cpyref/actions/runs/38626748383) 读取全部 2,260 条正式记录，检查任务/组/重复编号唯一且完整，重新计算各组通过数及逐题中位数、p95、调用数、字节数，并核对已记录的输出摘要与保护条件。原始 JSONL 共 2,753,428 字节，SHA-256 见 audit.json。

这次核对是重新计算保存的数据，不是第二次执行产品。临时输出在原试验结束后已清理，核对程序不能重新读取那些输出；原始执行时的字节验收和摘要仍由 runner 记录。这一限制不能省略。

**真实 Agent 有/无 cpyref 对照尚未运行。** 当前没有模型成功率、输入/输出/缓存/推理 Token、费用、端到端模型时间或学习成本的测量。完整后续实验设计见 [README 第 6 节](README.md#6-真实-agent-ab-协议)。需要固定可实际调用的模型版本与运行环境，收集真实使用记录，并在全新独立会话中执行同一批目标；不应使用本轮工具数据填充缺失的模型结果。
