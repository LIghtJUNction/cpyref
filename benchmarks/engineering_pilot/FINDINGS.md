# CpyRef 软件工程效率实验：首轮实测结论

实验日期：2026-10-15。产品代码未修改，实验及原始记录保存在 PR #6 的独立分支。

**结论：这轮没有证明 CpyRef 可以提高软件工程任务效率或降低成本。也不能据此认定 CpyRef 无效。主要限制是基线完成率过低、模型响应超时，以及模型没有正确使用新增工具。**

## 测试了什么

已确认 v0.3.0 发布。本实验从当时最新 Git 主分支提交 `0c869fdc31e21490a6a7cbfa90f9e0229c46af04` 编译安装 CpyRef 0.3.0，保留安装日志和可执行文件 SHA-256。没有使用旧基准二进制。

同一个 Qwen3-4B-Instruct-2507 Q4_K_M 模型实际生成操作命令。六个构造的软件维护任务，各运行原生工具组与 CpyRef 可用组，共 12 次尝试。它们有实际代码、文件和可执行验收，但不是从 GitHub 真实 issue 抽样的任务，也不是 SWE-bench。四项任务偏向原文复用，两项是诊断和纯逻辑对照。

原生组保留 shell、Python、cp、sed、grep 和管道；没有禁止高效的原生命令。实验组额外提供 CpyRef 与使用说明，是否调用由模型决定。两组均最多 5 轮模型响应，每轮最多生成 768 Token；命令限时 20 秒，模型请求限时 180 秒。两组使用同样的输出展示上限。所有失败均保留，没有选择性重跑。

模型操作在没有网络、没有凭证、看不到答案的独立容器内执行。验收代码在模型任务结束后运行。每个初始任务均已验证不能通过验收，预设正确解均能通过。

预先固定的规则见 [PROTOCOL.md](PROTOCOL.md)。实际模型运行见 [38671711888](https://github.com/LIghtJUNction/cpyref/actions/runs/38671711888)。

| 通过本轮验收 | 0 | 1 |
| 模型调用完整，但未通过验收 | 4 | 4 |
| 模型响应超时，调用记录不完整 | 2 | 1 |
| 出现 CpyRef 调用的任务 | 0 | 2 |

**上表 Token 是已收到的 usage 之和。超时请求缺少完整 usage，所以它们是整组消耗的下限，不是完整成本。不能用两列直接计算节省或增费百分比。** 时间是每次尝试计时的总和，不是并行执行整批任务的墙钟时间；包括失败和超时等待，但不包括下载、模型启动和编译安装，不能外推为商用 API 的开发时长。

## 原始记录暴露了哪些问题

### 1. 模型误解了引用的传递方式

`port_parser/cpyref` 中，模型混用了行号和起止标记选择器，并生成 `cpyref copy ... | cpyref insert - ...`。工具实际要求完整引用编号，不能把这里的 `-` 当成自动读取上游编号。调用分别返回 `INVALID_ARGUMENT`、`INVALID_REF`，任务未完成。

这些失败可以定位，不是推测。该任务的目标文件最终哈希仍等于初始文件哈希；工具拒绝了无效操作，没有完成要求的插入。原生组也发生了 shell 引号错误，随后写出了不符合精确字节要求的目标。不能把两组失败称为效率提升。

证据：[实验组逐轮记录](results/38671711888/shard-1/port_parser-cpyref/trace.json)、[原生组逐轮记录](results/38671711888/shard-1/port_parser-native/trace.json)。

### 2. 接入说明与操作预算本身也是变量

`sync_config/cpyref` 中，模型直接执行了没有 `cpyref` 前缀的 `copy`，并遗漏 insert 的引用参数。本实验提供的简化指南把一些子命令缩写为 `copy FILE`、`insert ID FILE`；这一写法可能增加了误解，不能把全部问题归因于产品二进制。另一方面，指南已经给出过完整的 shell 变量示例，模型没有正确采用。

5 轮预算下，读取源码、读取目标、预览、处理引用和真正写入容易挤占完成任务的机会。本轮基线也大量失败，因此它没有把模型能力、接入说明和工具效果充分分开。

证据：[配置同步逐轮记录](results/38671711888/shard-2/sync_config-cpyref/trace.json)。

### 3. 输出更短不等于完成同一任务更便宜

在函数移植任务中，原生组输入/输出为 `3953/904`，CpyRef 组为 `5697/536`。输出减少了，但输入增加了，且两组均未通过验收。不能只取输出 Token 的下降作为宣传数字。

### 4. 本轮运行环境不足以验证完整成本

三个请求在 CPU 推理时达到 180 秒客户端超时：`extract_table/native`、`extract_table/cpyref`、`sync_config/native`。没有收到完整响应的请求不能按零 Token 计费。模型、运行库和容器的记录身份在三个分组间一致，已收到的 49 份响应的 usage 与结果加总一致；52 次请求中的 3 次仍然缺失完整 usage。加法核对通过，不代表完整成本验证通过。

使用本地模型，没有支付模型 API 费用，但计算资源的货币成本未测量。不能声称实验成本为零，也没有实际商用账单节省证据。

## 对下一轮实验的具体要求

先做独立校准：确保模型能完成这类维护任务，确认提示里的完整命令能被正确理解，避免客户端超时遮蔽任务结果。当前 4B 模型与 5 轮预算没有形成有判别力的基线。

把“模型会不会选择 CpyRef”和“选用后是否有效”分开测。保留自由选择实验；另设固定操作阶段的实验，检查同一片段、同一目标、同一验收下的调用成本。不得把固定脚本实验包装成自主 Agent 提效结果。

产品接入应优先减少引用转交、哈希提取和选项组合的出错机会。可以用参数明确的工具接口或短事务编号组织预览与提交，但继续验证目标文件版本，不能用取消安全检查换取速度。

有效正式实验还需要真实仓库维护任务、多个模型、多个随机种子，完整计入说明、读取、重试、失败和缓存收费，并先检查验收质量。这些条件本轮尚未满足；本报告没有把待完成工作写成结果。

## 数据保留与核查

初次环境准备失败的运行 [38671521198](https://github.com/LIghtJUNction/cpyref/actions/runs/38671521198) 已单独保留。它在模型运行前失败，原因是下载脚本没有处理 llama.cpp 稳定版到二进制 nightly 版本的跳转。修正仅涉及下载，未改变任务、模型、预算或评分。

独立的 [模型接口自检](https://github.com/LIghtJUNction/cpyref/actions/runs/38673018227) 能返回正确的 JSON 动作，但不是软件工程任务成绩。没有将其纳入 12 次尝试。

原工作流生成的 `summary.json` 与 `REPORT.md` 保留原样，已标记完整性失败。其中 Token 和价格权重之和只覆盖已收到的 usage，不能当成完整账单或可靠的每成功任务成本。解释与最终结论以本文件和 `AUDIT_SUMMARY.json` 为准。独立复核命令：
